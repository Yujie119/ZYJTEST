# 全候选库覆盖主问题与完整资源调度搜索

本目录是 2026-09-24 最终复核阶段的独立搜索分支，保持原题物理系数及已经核验的 O01 充换电子模型。默认共享电池初始在 O01；方案没有携带备用电池，也没有假定服务区存在额外电池库存或供电能力。

## 方法及结论边界

1. 读取 `改进搜索_20260924/frozen_evaluation_candidates.json.gz` 的 28,216 条实际可行候选路线，对 80 个货箱建立恰好覆盖一次的 0-1 主问题。架次数为变量；无架次数等式。
2. 主问题以架次、能耗和按机型无人机工作量的折中生成新的箱组和访问路线。设置少量 N 或 E 上限只是 ε 探测条件，所有可行结果统一入档；未规定最终架次数为 22，也未规定不得超过 22。
3. 主问题中的工期变量仅受机型工作量约束，是搜索代理，不是实际可执行完成时间。各机型还施加根据路线硬截止计算的必要累计工作量约束。主问题得到整数覆盖，不代表已取得可执行方案。
4. 对选定路线使用生产 `JointModel(..., mandatory=True)`，同时重新安排实际无人机、电池编号和连续开始时刻，落实无人机不重叠、电池全充后复用、逐箱硬时限以及真实迟到指标。
5. 全部调度结果必须经过 `verify_plan`；失败、不可行和限时无解均单独记录，不作为可行结果。`objective[2]` 是全部运输架次返回 O01 的最晚时刻，与最后一次交货、累计飞行时间及最后一块电池充满时刻有区别。

固定路线调度返回 `Optimal` 时，只证明该固定路线集、该次记录的权重目标的调度最优。全库主问题限时界差、工作量代理下界均不能证明完整原问题全局最优。

## 复现与文件

- `search_cover_master.py`：首轮实际执行的代码；24 个探测任务、4 个进程，每个覆盖 MILP 12 秒、调度 MILP 12 秒。实际总墙钟时间见 `summary.json`。
- `search_cover_master_warm.py` 与 `run_warm_wave.py`：第二轮代码，用已核验方案作为覆盖主问题初解，8 个探测任务、4 个进程，每个覆盖 MILP 15 秒、调度 MILP 12 秒。
- `config.json` / `warm_config.json`：权重、ε、随机种子、时间预算及候选文件 SHA-256。
- `cover_*.json` / `warm_*.json`：各任务的主问题状态、所选候选编号、完整实际方案、资源调度状态和核验结果。
- `archive.json`：首轮新增解的非支配档案；`combined_archive.json`：第二轮与首轮合并的新档案。最终主流程需进一步与既有档案及其他搜索分支合并，不能只在本分支单独选定提交方案。
- `solver_log.json` / `warm_solver_log.json`：全部成功及失败任务；`summary.json` / `warm_summary.json`：汇总。

首轮 24 个任务中，12 个落实为核验通过的资源方案；共保留 7 个本分支非支配目标向量。最有代表性的两个新增方案为：

| 架次 | 总能耗/kWh | 全部返回 O01 时间/s | 时间/min | 加权迟到/s |
|---:|---:|---:|---:|---:|
| 20 | 65.4625120826 | 6881.65584867 | 114.69426414 | 0 |
| 22 | 65.5185167168 | 6206.34444344 | 103.43907406 | 0 |

这说明原先 28 架次方案的主要问题至少包括搜索不足；新方案没有为了接近他人参考数字而修改能耗公式、覆盖规则或时限规则。具体源头假设的最终审查结论应以主流程报告为准。
