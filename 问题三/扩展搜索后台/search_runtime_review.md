# 问题三扩展搜索后台运行审查建议

本文档供后台长时间搜索脚本使用。它只提出运行和验收要求，不修改现有求解器、正式结果或原始候选库。

## 1. 运行范围与输出隔离

- 后台搜索只能读取原始附件、只读DEM、原始1292条候选和独立扩展候选；不得覆盖 `问题三/子问题一/累计候选路线.json`、`问题三/子问题二/最终方案.json`、正式Excel或现有缓存。
- 每次运行建立带时间戳的新目录，例如 `问题三/扩展搜索后台/runs/20260924_...`，在启动前写入 `run_config.json`、输入SHA-256和候选库SHA-256。
- 旧库的MILP下界、上界和档案不自动迁移。加入134条新模式后必须重建候选库指纹、重新计算边界和重新核验；旧界只作为历史对照，不能作为扩库后的界。
- 新扩展库默认记录为1426条模式记录（原1292+缺失134），随后由同一实例展开规则生成副本。模式记录、实例记录、实际核验通过方案必须分开存储。

## 2. Windows隐藏启动与硬期限

建议由PowerShell 7启动独立隐藏子进程，不在主窗口中复用当前Python进程：

```powershell
$py = 'E:\tool\anaconda3\python.exe'
$script = 'D:\研究生\比赛\数学建模\2026\问题三\扩展搜索后台\run_q3_background.py'
$run = 'D:\研究生\比赛\数学建模\2026\问题三\扩展搜索后台\runs\20260924_120000'
$p = Start-Process -FilePath $py -ArgumentList @('-X','utf8',$script,'--run-dir',$run,'--deadline-s', '7200') -WindowStyle Hidden -PassThru
$p.Id | Set-Content -LiteralPath (Join-Path $run 'launcher_pid.txt')
```

脚本内部仍须记录Python PID、父PID、启动UTC时间、墙钟期限和子进程PID。硬期限应使用单调时钟：

\[
t_{deadline}=t_{start}+7200\text{ s}.
\]

在期限前预留清理窗口（例如30—60 s），先停止提交新任务，再等待当前短MILP调用结束，最后仅终止本次运行登记的PID树。不能按进程名杀掉其他问题或其他用户的Python/HiGHS进程。

## 3. PID登记与安全终止

启动每个求解子进程时，立即把PID、命令行摘要、开始时刻和所属阶段追加到 `process_registry.jsonl`，使用文件锁或原子追加。终止流程应：

1. 读取本次运行自己的登记PID集合；
2. 检查进程命令行或父子关系仍属于本次 `run_dir`；
3. 先发送温和终止请求；
4. 只对仍存在且身份匹配的PID执行强制终止；
5. 将终止原因、时间和退出码写入登记文件。

禁止使用按名称全局终止、按模糊命令行匹配终止或递归杀整个Python树。若PID已退出或被系统回收，记录状态即可，不重复杀新复用的PID。

## 4. 周期进度与中间结果

每30—60 s写入一次 `heartbeat.json`，至少包含：

- 单调时间、墙钟时间、当前阶段和当前迭代；
- 已运行秒数、剩余秒数、当前子任务PID；
- 候选模式/实例数量、已加载通信块、已加载资源对；
- 当前已核验可行方案数、最好四目标、C/E/N/L上下界；
- 最近一次求解状态、HiGHS退出码、MIP gap、约束残差；
- 失败计数、连续失败计数和下一次退避时间。

每次获得候选方案后先写 `candidate_XXXX.json.tmp`，完成JSON校验、独立资源/通信核验和SHA-256后再原子重命名为正式候选文件。未通过核验的方案只能写入 `rejected/`，不能进入当前最好方案或正式档案。

## 5. 重启与失败控制

后台协调器必须区分：

- 正常限时但有可行解；
- 求解器限时无可行解；
- 输入/代码错误；
- 进程异常退出；
- 机器资源不足或CUDA/CPU初始化失败。

只有进程异常退出或明确的瞬时资源失败允许有限重启。建议同一阶段最多重启2次，使用指数退避（例如15 s、60 s），每次重启保留新的PID和日志，不覆盖旧日志。输入错误、候选指纹不匹配、独立核验失败不得盲目重启；应标记为 `blocked_input_or_validation` 并停止该链。

重启只能从最近一次原子保存的状态继续。状态必须包含候选库指纹、已加载通信块、资源对、随机种子、目标模式和剩余期限；状态与新输入不一致时拒绝恢复。

## 6. 长跑候选库与验证顺序

推荐阶段顺序：

1. 读取并核验原1292条模式与新增134条单站模式，生成1426条模式清单；
2. 根据 `pattern_id` 和需求计数生成实例副本；
3. 先运行候选/物理字段回归检查，不启动MILP；
4. 再进行低成本结构可行性检查；
5. 最后进入全库直接MILP或ALNS对照。

每个新模式至少检查：目的地与访问顺序一致、载荷质量/体积、整架次总能耗与返航余量、医疗/首批时间系数、连续通信 `needs` 和唯一模式签名。新模式必须能追溯到原始工作簿版本和生成脚本版本。

## 7. 结果声明边界

扩展库运行结束后分别报告：模式库规模1426、实例库规模、已认证可行上界、同一固定模型下求解器有效下界、界差、核验通过率和运行预算。不能把“加入134条单站模式后没有改善”解释为全部路线空间没有改善；跨区路线仍未完整枚举。

若长跑只获得外部已知方案，应标注为“外部基准映射/已知上界”，不能写成新搜索发现。正式提交结果仍保持不变，除非用户另行确认替换。
